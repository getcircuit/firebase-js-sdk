# Makes @firebase/firestore {{FIRESTORE_VERSION}} (firebase {{FIREBASE_VERSION}}) do work per server update in
# proportion to what changed, not to everything the client holds live, keep one
# copy of a document's fields where it kept one per cache entry and per view,
# build each reference's path string once instead of on every read, keep
# the split array when parsing a lone path string instead of copying it twice,
# and classify each value by its key when converting or sizing documents.
#
# Why: on every server update (remote event), local write, ack or bundle load, the
# client revisits every listener's view and some per-listener state. A page holding
# ~370 listeners and ~24,000 documents and receiving ~15 updates per second spent
# most of its main thread inside the SDK, about 80% in one walk
# (View.updateLimboDocuments).
#
# Changes, by SDK source name:
#
# 1. View.applyChanges / View.updateLimboDocuments
#    Limbo documents are documents a view shows that the server has not confirmed
#    for its query and that have no local writes. Upstream recomputes that set by
#    walking every document in the view on every update ("TODO(klimt): Do this
#    incrementally"). Now each update rechecks only the keys in its change set plus
#    the keys the target change added or removed. The limbo documents count as
#    unchecked from the start of each update until it finishes, so an update that
#    skips the limbo step (secondary tab, target pending reset, view not current,
#    offline), throws midway, or replaces the synced keys
#    (synchronizeWithPersistedState) leaves the next one to walk every document as
#    upstream does. A view that has ever held a key with a numeric id segment always
#    walks every document: numeric ids compare by value, so one key can be spelled
#    several ways (__id5__, __id05__) and malformed ones make comparisons throw, and
#    only the full walk reports the spelling the view holds and throws where
#    upstream throws. Limbo changes come out in upstream's order: removed keys, then
#    added keys, each in key order.
#
# 2. WatchChangeAggregator.createRemoteEvent
#    For each current single-document target, upstream called
#    ensureDocumentUpdateByTarget, which inserts an empty entry into
#    pendingDocumentUpdatesByTarget, a sorted map, on every update. Nothing reads
#    those entries. A plain lookup gives the same answer.
#
# 3. compareUtf8Strings
#    Returns 0 for equal strings before comparing character by character. Numeric
#    ids (__id5__) still take their own branch in BasePath.compareSegments.
#
# 4. ObjectMap.get
#    Returns a stored value whose key is the looked-up object before running the
#    deep equality function. Every equality function the SDK passes is reflexive.
#
# 5. KeyFieldInFilter / KeyFieldNotInFilter (documentId() in / not-in)
#    The sync engine offers every changed document to every view, and each filter
#    scanned all its keys with DocumentKey.isEqual. The filters now group keys by
#    document id and confirm candidates with isEqual. Numeric ids compare by value
#    and malformed ones throw, and an empty path has no id, so a list or key with
#    either is scanned in order as upstream does.
#
# 6. View.computeDocChanges
#    The sync engine offers every changed document to every view, and each view
#    looked the document up in its own document set before checking its query.
#    Every document a view holds matched its query, and the query's path check
#    depends only on the key, so a document outside the query's path can be neither
#    in the view nor a new match. Views now skip such documents before the lookup.
#    Pipelines are never skipped, and neither are keys with numeric id segments,
#    because the path check compares segment spellings while the document set
#    compares numeric ids by value. An entry whose map key and document key are
#    spelled differently is never skipped and marks the limbo documents for a full
#    check.
#
# 7. doc(collectionReference, path) types (firebase/firebase-js-sdk#7826)
#    The overload accepted `path?: string`, so doc(reference, undefined) compiled
#    and then threw at runtime. It is now doc(reference) for a generated ID and
#    doc(reference, path: string, ...pathSegments). Only the type rollups change.
#
# 8. ObjectValue / MutableDocument.mutableCopy (memory)
#    The memory cache hands out a copy of a document on every read, and stores one
#    on every write, so views do not see each other's local writes. Each copy
#    deep-cloned the document's fields: a document held by the cache and by four
#    views was stored five times. A copy now shares the fields until either side
#    writes through set(), setAll() or delete(), which copy them first. Each
#    copy still has its own version, read time and pending-write state. clone()
#    still copies the fields at once; the SDK uses it where raw fields leave its
#    control.
#
# 9. ResourcePath.canonicalString (DocumentReference.path, CollectionReference.path)
#    Upstream copied and joined the path's segments on every call. Each path now
#    keeps the string from its first call. Paths never change after construction,
#    and the field is set in the BasePath constructor so every path has the same
#    object shape. A reference whose path was read is no longer structurally
#    equal to an equal one whose path was not: tests that compare references
#    with toEqual or deep.equal should compare paths or use refEqual instead.
#
# 10. ResourcePath.fromString (watch stream resource names, documentId() in / not-in)
#    Upstream split each path string, filtered out empty segments and spread
#    the result into a new array. A lone component that passes the // check
#    and splits into no empty segment now keeps the split array as its
#    segments. Every other input takes upstream's code, so results and thrown
#    errors stay the same, with one exception: upstream's spread throws
#    RangeError for a lone component with no empty segment past the engine's
#    argument limit (between 60,000 and 130,000 segments in Node 24), and
#    such a component now parses. Upstream already builds such a path from
#    several shorter components, and persists writes and document listens on
#    it in IndexedDB, but throws when a documentId() filter or the IndexedDB
#    decoder parses its resource name back. With this change those parses
#    succeed too, so a target with such a filter is now persisted as well,
#    and an unpatched SDK reading it back throws. Firestore allows at most
#    100 levels of subcollections, so the backend rejects such a path.
#
# 11. typeOrder, AbstractUserDataWriter.convertObjectMap, estimateMapByteSize
#    (DocumentSnapshot.data() and get(), the memory LRU cache's document size)
#    typeOrder classified a value by testing `'nullValue' in value`, then
#    `'booleanValue' in value` and so on, up to ten checks before mapValue.
#    Values of different kinds have different object shapes, so these lookups
#    run at V8's slowest (megamorphic) speed. typeOrder now reads the value's
#    keys with for...in and looks each one up in a single switch that names
#    every document-value member of the value_type oneof with its precedence
#    and type order. A well-formed value has one key, so this is one lookup. A
#    value with several members is classified by the one with the lowest
#    precedence, which is the order upstream tested them in, and a value with
#    none fails as before. A mapValue is still checked for a server timestamp,
#    the max value and a vector. Members must be enumerable keys, as in JSON,
#    protobufjs output and object literals: a non-enumerable property, or a
#    Proxy hiding a key, is not seen. A primitive throws upstream's TypeError,
#    after for...in has walked it (a long malformed string's characters
#    included). The two per-field map walks behind data() and the size
#    estimate loop over the fields directly instead of calling a helper's
#    callback per field, and still skip inherited fields.
#
# Behavior: changes 1-6 and 8-11 return the same results, emit the same limbo changes in
# the same order and throw the same errors as upstream, except change 10 for a
# lone component with no empty segment past the engine's argument limit, and
# the hidden or non-enumerable members change 11 names, which no SDK path
# builds. Checked on the branch:
# - Firestore's unit and spec suites, in memory and with mock IndexedDB
#   persistence including multi-tab specs, give the same results as the release
#   tag: any test that fails also fails there.
# - test/unit/core/view_review_cases.test.ts: nine edge cases from code review
#   (malformed numeric ids with limbo off, mismatched map entries with limits and
#   refills, an update that throws midway), each expecting the result recorded
#   from the {{FIREBASE_VERSION}} View. Each earlier draft that had one of these bugs
#   fails them.
# - test/unit/api/doc_overloads.test.ts fails to compile against the upstream
#   doc() overloads (change 7).
# - view_limbo_fuzz.test.ts compares the limbo documents with a full recompute
#   after every call, including keys that spell one numeric id two ways.
# - key_in_filter_fuzz.test.ts compares the key filters with a plain isEqual
#   scan, thrown errors included (400 seeds).
# - object_value_copies.test.ts runs random set/setAll/delete/copy sequences on
#   shared copies and on deep copies (300 seeds) and expects the same fields. The
#   memory cache and LocalStore tests check that cache reads share fields, and that
#   documents a remote event returned keep their fields through a later local write
#   and its rejection.
# - path.test.ts reads a path's string, then checks the strings of its child,
#   popLast and popFirst, which share its segment array, and its own again.
# - path_from_string.test.ts compares fromString with upstream's code over
#   fixed and random path strings (200 seeds of 50 inputs: empty, leading,
#   trailing and doubled slashes, several components, unicode), thrown errors
#   included, and checks that a lone component keeps the split array.
# - type_order.test.ts compares typeOrder with a copy of the release's
#   typeOrder on a value of every kind (server timestamps, min and max values,
#   vectors), on malformed values (no member, unknown, undefined, inherited,
#   pipeline-only and several members) and on 2,000 random sets of members in
#   random order, errors included. It compares data() under each server
#   timestamp behavior, and the size estimate, with copies of the release's
#   conversion and sizing on the same values, a document of every kind and 300
#   random documents.
#
# Measured with the same changes (emulator: a second client holding documents
# live, CPU per update):
# - One query holding 10,000 documents 27.6 -> 0.4 ms, 334 batch queries over
#   10,000 documents 10.2 -> about 1.5 ms, 10,000 document listeners 113 -> 33 ms,
#   366 queries over 24,300 documents 25.8 -> about 1.45 ms.
# - 10,777 changed documents offered to 360 `in` filters of 30 ids: 17-20 s ->
#   0.16 s.
# - On the live page above, 60-240 s after load: event-loop delay p95 83-96 ->
#   31-42 ms, long-task share 12-13% -> 2.5-10%. First publish (~40 s) is unchanged.
# - Change 8, heap after GC with a second client holding 300 documents of about
#   50 nested maps each (memory cache, Node, 3 runs): one query +20.0 -> +13.7 MiB;
#   four more queries over the same documents +27.5 -> +2.2 MiB, their first
#   (cached) snapshot 54-66 -> 15-19 ms. Remote updates, offline writes and acks
#   take the same time, and every listener matches a server read at the end.
#   On the live page above (a 4.16.0 build with the same code; three pairs of runs,
#   alternating which build goes first), the JS heap after a forced GC 240 s after
#   load fell 1,087 -> 1,010, 1,295 -> 1,122 and 1,324 -> 1,246 MB (6-13% less).
#   Time to first publish and long-task share stayed within run-to-run noise.
# - Change 9, Node, built node bundle: a repeated DocumentReference.path read
#   at depth 2, 4 and 6 takes 38, 59 and 79 ns and 145-264 B, and 4 ns and 0 B
#   with the stored string. First reads cost the same; each path is 8 B larger.
#   Emulator, three alternating pairs, CPU ms per update: 10,000 document
#   listeners 38.9-40.9 -> 35.3-39.5, 366 queries over 24,300 documents
#   1.9-2.5 -> 1.4-1.6. Opening the listeners took the same time.
# - Change 10, query building rather than updates: Node 24.18, built node
#   bundle, five alternating rounds. Building
#   query(collectionGroup(db, 'messages'), where(documentId(), 'in', refs)) with
#   30 references takes 16.7-20.0 us (median 17.2), and 10.9-13.2 us (median
#   11.2) with the split array kept.
# - Change 11, Node 24.18, built node bundle: 2,000 documents of 30 nested
#   maps each loaded from a bundle, identical data() output, medians of 12
#   alternating runs: data() 36.2 -> 16.6 us per document, the LRU cache's
#   size estimate 27.7 -> 8.2 us. With the typeOrder change alone, 21.2 and
#   13.1 us. Comparing many values of one shape costs a little more, because
#   for...in has a setup cost that upstream's `in` checks, specialized to that
#   one shape, did not: a cached query over 12,000 documents took 3-5% longer
#   ordered by an integer field and 0-4% longer by a string field (two runs,
#   medians of 6).
#
# Files: the main build's bundles that change (the common-* chunks and
# intermediate/), and the type rollups that change
# (dist/*.d.ts, dist/lite/*.d.ts). The lite/ bundles are not rebuilt and stay as
# published, and neither are the per-module declarations under dist/firestore/.
#
